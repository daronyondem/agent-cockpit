# Agent Project Memory

This file mirrors stable project memory that should shape future agent work in
this repository. Durable workspace memory remains the source for full historical
context; this document captures the project rules and decisions that are
important enough to keep connected from `AGENTS.md`.

When a durable memory becomes a recurring project rule, update both durable
memory and this file. Do not write fallback local memory files if the memory
tool is unavailable.

## Agent Workflow

- `AGENTS.md` is the canonical cross-agent guidance file for this repository.
  When maintainability, architecture, release, or verification patterns become
  stable, update `AGENTS.md`.
- Keep changes surgical. Every changed line should trace to the user request.
- Use GitHub CLI for normal GitHub work. Do not create draft PRs unless the user
  asks for a draft.
- Do not use auto-closing issue keywords in commits or PR bodies unless the user
  explicitly says the PR fully resolves the issue.
- PR readiness includes tests, `npm run lint`, behavior/spec updates, ADR
  evaluation, mobile PWA impact evaluation, and `AGENTS.md` evaluation.
- `npm run lint` is a zero-warning gate. Intentional
  `react-hooks/exhaustive-deps` inline disables must include a written reason.
- Jest coverage thresholds live in `jest.config.js`. When meaningful backend
  coverage is added, raise thresholds toward the new baseline in the same PR;
  do not lower thresholds just to merge a regression.
- ADR lint validates `affects:` paths unless the ADR is tagged `historical` or
  the path is under a retired prefix listed in `scripts/adr-lint.js`.
- Public docs and issue/PR text should avoid leaking private workspace context.
- If `memory_note` fails, do not create or edit local memory fallback files.
  Report the failure instead.
- Browser-visible stream frames belong in browser-safe
  `src/contracts/streamFrames.ts`. Backend adapters can use broader server-only
  stream events, but web/mobile clients should consume only the shared browser
  frame union. Desktop stream-frame state transitions belong in the pure reducer
  under `web/AgentCockpitWeb/src/stream/`, with `streamStore.js` acting as the
  socket/API/timer effect adapter.
- Server type definitions live in declaration-only domain modules under
  `src/types/` and are re-exported through `src/types/index.ts`. Contracts
  keep importing exactly `../types`; new server-only types should go in the
  matching domain file rather than the barrel.

## Releases And Installers

- Production installs update from GitHub Releases. Development installs track
  `main`. Do not add extra release channels unless that decision changes.
- Release procedure belongs in repo markdown outside GitHub Actions and is
  linked from `AGENTS.md`.
- Per-release documentation should be generated by automation rather than
  drafted manually from scratch.
- GitHub Release bodies should be concise and user-facing. Avoid extra section
  headers such as "Shipped For Users" and "Developer Details"; link detailed
  developer docs instead.
- Installer, release packaging, install-state, install-doctor, and self-update
  changes must preserve already-working macOS production behavior.
- Windows fixes must be explicitly Windows-specific and platform-gated. Run
  macOS regression coverage before release when installer/updater/welcome
  behavior changes.
- Linux production release support targets Ubuntu 24.04 LTS x64/glibc first.
  Keep Alpine/musl, NixOS, WSL, Linux arm64, and 32-bit Linux unsupported unless
  a later tested decision changes the support matrix.
- macOS and Linux installers register current-user session startup by default
  while keeping PM2 as the app supervisor. macOS uses
  `~/Library/LaunchAgents/com.agent-cockpit.server.plist`; Linux uses the
  `agent-cockpit.service` systemd user unit. `--no-auto-start` records
  intentional manual startup. Do not replace this with privileged LaunchDaemons,
  system services, or no-login operation without a new ADR.
- POSIX self-update restart launchers must not depend on the executable bit of
  `<dataDir>/restart.sh`. Launch through `sh`, chmod after every write, repair
  stale restart scripts on fixed-server startup, and have macOS/Linux installer
  repair runs chmod stale restart scripts before PM2 starts the app.

## macOS Install Path

- macOS was the first supported production installer path and should remain
  stable while Windows is improved.
- The macOS installer should not assume Node/npm already exist. It can use a
  private Node runtime to support fresh Macs.
- Do not assume Homebrew is installed on macOS. Homebrew can be mentioned only
  as an already-installed option; official installers/downloads remain valid
  fallbacks.
- macOS production self-update uses the Darwin Node tarball and stable
  `runtime/node` symlink behavior.

## Windows Install Path

- The Windows installer is a first-class path, not a port of the macOS shell
  installer.
- Default Windows install is per-user and interactive-login only under
  `%LOCALAPPDATA%\Agent Cockpit`.
- Do not make Windows Service/no-login mode, admin install, global Node, PM2
  global install, Electron, Tauri, or MSI the default path.
- Use a private Node 22 ZIP fallback, install-local `PM2_HOME`, and a
  current-user `ONLOGON` scheduled task.
- Windows must not show visible Node console windows. PM2 may manage the app,
  but the process launched on the desktop must stay hidden.
- Windows installer repair reruns must not delete an existing private Node
  runtime directory. PM2 or Agent Cockpit may hold `node.exe` open; reuse a
  verified runtime or install a sibling replacement.
- Windows private-runtime reuse must verify npm JavaScript entrypoints
  (`npm-cli.js`, `npx-cli.js`, `npm-prefix.js`) and native command exit codes.
  `.cmd` presence alone is not enough.
- Windows Install Doctor should resolve npm/npx from installer-recorded
  `nodeRuntime.binDir` when present.
- Windows PM2 cleanup and startup should resolve app-local
  `node_modules\.bin\pm2.cmd` directly. Windows Install Doctor should probe the
  app-local PM2 package through `node.exe node_modules\pm2\bin\pm2 --version`.
  Do not invoke `npx` from freshly extracted or partially repaired app
  directories.
- Windows Install Doctor should install Claude/Codex npm CLIs into
  `<installDir>\cli-tools` with `npm --prefix <installDir>\cli-tools i -g ...`,
  persist that directory on both the live server `PATH` and the current user's
  Windows `Path`, and prefer the real package entrypoints npm installs under
  that prefix (`claude.exe`, `codex.js` through `node.exe`) before falling back
  to `.cmd` shims. If user `Path` persistence fails after npm succeeds, treat it
  as a warning step and continue wrapper repair plus refreshed detection.
  Windows backend, auth, doctor, plan-usage, and CLI-update launches should
  share that resolver rather than spawning npm shims directly. Detection must
  still recognize self-installed `claude`/`codex` commands from the user's
  Windows `PATH`. When a PATH directory contains npm's global package layout,
  prefer the package entrypoint next to the PATH-visible shim before spawning
  `claude.cmd` or `codex.cmd`.
- Manual Windows development startup builds should invoke `npm.cmd` through the
  existing `.cmd` wrapper path; bare `npm` can fail under Node `execFile` even
  though the production installer path works.
- Windows production self-update should also repair the current user's `Path`
  for `<installDir>\cli-tools` so existing installs gain terminal CLI access
  after updating without rerunning the full installer.
- Windows Agent Cockpit-managed Codex and Grok Build terminal wrappers should
  call the recorded private `node.exe` plus the package entrypoint
  (`<installDir>\cli-tools\node_modules\@openai\codex\bin\codex.js` or
  `<installDir>\cli-tools\node_modules\@xai-official\grok\bin\grok`)
  directly. Installer repair reruns, Install Doctor, self-update, and CLI update
  paths should all repair stale npm-generated wrappers. Do not depend on a
  global `node.exe`, and do not add the private runtime directory to the user's
  Windows `Path` unless that product decision changes.
- Production self-update must not accept generic HTTP liveness as success. The
  generated restart script must require `/api/chat/version.version` to match the
  target release version. Windows restart/rollback must use the target and
  rollback releases' app-local `pm2.cmd` paths if it has to restore the previous
  release.
- Windows installer ZIP extraction should stay non-interactive. Prefer the
  script's `System.IO.Compression.ZipFile` helper over `Expand-Archive` in the
  user-facing installer so PowerShell archive progress cannot pause installs in
  Windows console hosts.
- Windows installer readiness checks should use raw .NET HTTP requests instead
  of `Invoke-WebRequest` against `/auth/setup`, so PowerShell page parsing or
  security prompts cannot pause the installer while waiting for the app.
- Windows self-update should avoid Unix-only assumptions such as `sh`, `nohup`,
  `tar`, `shasum`, symlink `current`, or junction dependencies.

## Mobile PWA

- Mobile direction is PWA-only. Native iOS/Expo work was evaluated but the
  current supported direction is the mobile PWA.
- Every feature or behavior change should explicitly evaluate mobile PWA impact:
  `mobile/AgentCockpitPWA`, `public/mobile`, UX, metadata, tests, and specs.
- The mobile PWA should preserve app-like chrome, realtime behavior without
  manual refresh, workspace picker behavior, queue/edit flows, and visual QA
  expectations captured in specs.

## Workspace Context, Memory, And Knowledge Base

- Workspace identity uses immutable `workspaceId` values. Absolute workspace
  paths are mutable metadata in `data/chat/workspaces.json`; legacy
  `workspaceHash` values and storage keys are compatibility/storage details, not
  the identity current clients should use.
- Data migration uses complete `AGENT_COCKPIT_DATA_DIR` bundles. Import is a
  destructive replace after backup, requires exact `REPLACE` confirmation, and
  does not merge destination conversations, settings, Memory, Workspace Context,
  KB SQLite/PGLite, or auth state. Keep migration specs/tests aligned when
  changing data-root layout or runtime-file exclusions.
- Workspace Context is the workspace-level operating memory feature. Its
  canonical data is markdown under `workspace-context/context/`, maintained by a
  configured CLI processor and exposed to active chat CLIs through an `AGENTS.md`
  instruction pointer rather than MCP.
- Workspace Context processor settings use global defaults with optional
  workspace overrides. Workspace overrides should store only the override, not
  copied global values.
- Workspace Context has its own processor category rather than implicitly
  reusing Memory or KB digestion settings.
- Workspace Context maintenance consumes accepted active Memory inbox entries
  and deletes those entries after folding them into context markdown. Do not
  reintroduce the old Memory Review scheduler/UI/MCP review workflow without a
  superseding ADR.
- Workspace Context public issue/PR content must avoid private context leakage.
- Workspace Context run logs are short-term operational records. Maintenance
  should prune `workspace-context/runs/*.md` and `state.json.runs` entries older
  than 7 days; durable learned context belongs in context markdown files.
- Workspace Routines are workspace-owned markdown workflows. Agent Cockpit owns
  authoring contracts, proposals, scheduling, run folders/history, and outreach;
  harnesses own task intelligence in `routine.md`. Keep lifecycle states minimal
  (`proposed`, `enabled`, `disabled`) unless a later ADR changes the model.
  Routines must be explicitly enabled per workspace before Agent Cockpit
  installs the managed `AGENTS.md` instructions, exposes routine actions, or
  runs scheduled routines; disabled routine reads remove stale managed
  instructions blocks without creating routine scaffolding, and disabling
  removes only the managed instructions block while preserving routine data.
- Memory update notifications should open a focused preview of the exact updated
  memory files before the full Memory listing.
- Memory consolidation should precede vector/embedding work where applicable.
- KB/media work should preserve current generated media if it already exists and
  avoid unnecessary churn.
- KB vector coverage or vector-index health issues should use the targeted
  vector-index rebuild path rather than full Re-Dream unless synthesis itself
  needs to be rebuilt.
- Welcome, Install Doctor, Settings, and KB upload checks should detect newly
  installed Pandoc/LibreOffice without requiring an Agent Cockpit restart.

- Agent Cockpit is not "Claude Code triads"; keep product framing backend-neutral
  and end-user oriented.
- Prefer direct, user-facing terminology such as "Agent Cockpit web UI"; avoid
  internal or provider-specific labels unless needed.

- Sidebar workspace commands and active-workspace actions should remain clear

- Answer product or design challenges directly; do not defend visual mismatches.

## Process Management

- `BackendRegistry.shutdownAll()` also runs after CLI updates, so adapter
  shutdown must permit subsequent runtimes and close stale startups after reset.
- Grok goal state reads require `sessionId` and workspace `cwd`; native subagent
  IDs differ from child session IDs. Keep fixture request validation strict.
  The macOS native suite covers questions/revised plans and goal
  set/pause/resume-to-active/pause/clear/status plus full autonomous completion.
  A small file goal took about 217 seconds through native ACP and 152 seconds
  through Cockpit; drain post-complete updates and keep an external deadline.
  Real valid-key/two-account runs and Windows/Linux certification remain pending.
- Grok session preparation is serialized per runtime. Goal status reads and
  pause/clear controls only attach an existing persisted native session (no
  creation, recovery, or MCP refresh); controls reserve the runtime before
  attaching, and every turn re-announces `external_session`/`backend_runtime`.
  Keep the restricted text wrap when a recovery prompt is prepended.
- Grok 1.0.52 API-key-only ACP sessions require headless `xai.api_key` auth,
  even when initialization advertises only `grok.com`. Cached terminal login
  takes precedence, and an empty isolated auth home cannot inherit it.

- Grok Build uses `grok-build` profiles and focused `grok*.ts` backend modules
  through ACP plus native extensions. Run `npm run e2e:grok-build` against an
  authenticated real CLI for version drift; the current native baseline is
  1.0.52 on macOS arm64, not a Windows/Linux compatibility claim.
- `npm run e2e:grok-build-ui` verifies real desktop/mobile behavior using an
  isolated PM2 fixture server and temporary data. Both native runners record
  CLI/OS/Node/git-state compatibility evidence. Do not run full Jest asset-build
  fixtures concurrently with browser checks; rebuild production assets after
  the full regression suite before checking the bundle budget.
- Restricted Grok calls must verify zero tool definitions and wrap slash
  commands as text. Keep auth-home isolation separate from shared CLI updates.
- Grok shell groups can detach. Preserve descendant PID/start-identity cleanup
  after root exit, drain background children and automatic parent continuation
  before finalizing usage, and never retry interrupted tool work. Details:
  `docs/spec-grok-build.md` and proposed ADR-0092.

- Use PM2 for local server management; do not run `node server.js` directly.
- Avoid adding npm scripts or update flows that accidentally restart Agent
  Cockpit via PM2 unless the request is specifically about server lifecycle.
- PM2 is acceptable for Windows when it stays install-local, per-user, and does
  not expose a visible console window.
