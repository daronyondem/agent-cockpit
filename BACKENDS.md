# Backend Comparison

Agent Cockpit supports multiple CLI backends. Not all backends expose the same metadata, so some features behave differently depending on which backend you use.

| Feature | Claude Code | Kiro | Codex | OpenCode | Grok Build | Cortex Code (CoCo) | Notes |
|---------|------------|------|-------|----------|------------| ------------------ |-------|
| Token usage tracking | Yes | No | Yes | Yes | Yes | Yes; input/output/cache buckets | Claude Code reports input/output/cache tokens. Codex reports per-turn token usage via `thread/tokenUsage/updated`. OpenCode reports JSON `step_finish.tokens`. Kiro reports credits + context % instead. Grok Build reports per-prompt `_meta.usage`, split into disjoint input/cache buckets and per-model rows. |
| Cost (USD) | Yes | No | No | Reported when OpenCode reports it | Reported model cost when complete | Unavailable; Snowflake pricing unknown | Claude Code provides per-message USD cost. Codex uses ChatGPT subscription credits or API-key billing — neither is exposed as USD per turn. OpenCode provider cost is passed through when present in JSON events. Kiro uses a proprietary credits system. Grok Build shows reported model cost only when the CLI reports it as complete; optional account balances are shown separately. |
| Integration protocol | Direct CLI spawn | ACP (JSON-RPC 2.0) | Codex App Server (JSON-RPC 2.0) | `opencode run --format json` | ACP + native xAI extensions | Dedicated native ACP adapter | Claude Code and OpenCode spawn a CLI process per message. Kiro, Codex, and Grok Build run persistent JSON-RPC servers (`kiro-cli acp` / `codex app-server` / `grok agent stdio`) with bidirectional streaming. |
| Visible thinking | Yes | Yes | Yes | Yes | Yes | Yes | Claude Code, Kiro, Codex, OpenCode, and Grok Build can all emit dedicated thinking frames. OpenCode streams `reasoning` JSON parts when Cockpit passes `--thinking`. |
| Plan mode | Yes | No | No | No | Yes | Yes; approval/revision | Claude Code and Grok Build expose plan approval flows. Grok Build plans also accept revision feedback. |
| Provider runtime mode | Ultracode on xhigh-capable Claude models | No | Fast speed tier | No | No | No | Ultracode is a Claude Code session setting, not a shared effort level or synthetic model. The composer shows a Claude-only Mode picker for xhigh-capable models and sends `--settings {"ultracode":true}` to standard or interactive Claude Code. |
| Goal mode | Set/clear/status; no pause/resume | No | Set/clear/pause/resume/status | No | Set/clear/pause/resume/status; soft budget | Deferred | Codex uses native thread-goal RPCs through `codex app-server --enable goals`. Claude Code uses its `/goal` slash command and transcript `goal_status` attachments, so Agent Cockpit hides pause/resume for Claude Code instead of emulating them. Grok Build sends native `/goal` commands over ACP; its token budgets are soft checkpoints that execution can exceed. |
| Tool activity visualization | Yes | Yes | Yes | Yes | Yes | Yes | Claude Code, Kiro, Codex, and Grok Build expose tool activity through their native stream protocols. OpenCode maps JSON `tool_use` parts, including built-in tools and MCP tools, into Cockpit tool activity and outcome events. |
| Model input capability metadata | Text + image | Per model; `auto`/Claude image-capable, open-weight entries text-only unless confirmed | Text + image | Parsed from `opencode models --verbose` | Text; verified image/PDF on grok-4.7 | Text; PNG on verified model/version | Media tasks fail closed when the selected/default model does not report the required input modality. OpenCode currently surfaces DeepSeek V4 Pro as `capabilities.input.image:false`, so that model is not available for KB image conversion or attachment OCR through OpenCode. |
| One-shot image transport | Native file/image tool | Explicit ACP image content blocks | Native file/image tool | `opencode run --file` for image/PDF-capable models | Explicit ACP images; native PDF file tool | Explicit ACP PNG; claude-sonnet-4-6 / 1.2.35 | KB image ingestion and chat attachment OCR require both this backend transport and model `input.image:true`. Memory, Workspace Context, KB digestion, and KB dreaming are text/tool workflows and are not image-gated. |
| Subagents | Yes | Yes | Yes | No | Yes, including background continuation | Deferred; generic tool activity only | Claude Code, Kiro, Codex, and Grok Build all fully demultiplex parent + child threads. Codex emits `collabAgentToolCall` items on the parent connection (with `tool`: `spawnAgent` / `sendInput` / `resumeAgent` / `wait` / `closeAgent`). Each completed `spawnAgent` carries `receiverThreadIds[]`; subsequent `item/*` notifications carry `threadId` at the params envelope (not in the README — verified via raw JSON-RPC capture), which the cockpit uses to attribute child tool activity back to its originating Agent card via `parentAgentId`. Grand-children (children of children) flatten to the same top-level card since the cockpit UI nests one level deep. Child-thread `agentMessage`/`reasoning` deltas are dropped (no per-child message stream in the UI); the child's final summary surfaces via `agentsStates[childTid].message` on the closing wait/closeAgent call. |
| MCP injection | `--mcp-config` flag | `mcpServers` in `session/new`/`session/load` | `-c mcp_servers.<name>.{command,args,env}=…` flags | `OPENCODE_CONFIG_CONTENT` | session/new and session/resume/load | Private explicit native plugin with stdio shims | Codex configures MCP via `[mcp_servers.<name>]` TOML sections. Cockpit injects them per-spawn via repeated `-c` overrides on `codex app-server`, so the user's real `~/.codex/` is used unchanged for auth, sessions, and config. OpenCode receives per-process local MCP entries in inline JSON config, so Memory/KB tokens are not written to OpenCode's global config. |
| Native memory import/watch | Yes | No | No | No confirmed native memory system | No; native memory disabled | No; native memory disabled | Claude Code exposes workspace memory files that Agent Cockpit can import and watch through `extractMemory()` / `getMemoryDir()`. Kiro and OpenCode do not currently expose a documented native durable-memory directory for Cockpit to import or watch. Codex has an experimental global `memories` feature, tracked below, but it does not fit Cockpit's per-workspace native-memory API. For OpenCode, use Agent Cockpit Memory through the Memory MCP tools. Grok Build's native memory is turned off (`GROK_MEMORY=0`) in Cockpit sessions; use Agent Cockpit Memory instead. |
| Mid-turn user input (stdin) | Yes | No | Yes (`turn/steer`) | No | Yes, native interject | Deferred; queued follow-ups | Claude Code writes additional lines to the CLI's stdin. Codex appends text to the in-flight turn via the JSON-RPC `turn/steer` request (no-op when no turn is active). Grok Build sends input through the native `_x.ai/interject` extension when no question or plan is pending. |
| Interactive user questions | Yes (`AskUserQuestion`) | No | Yes (`item/tool/requestUserInput`) | No | Yes, native reverse RPC | Yes; exact pending decision ownership | Codex's user-question request is EXPERIMENTAL and v2-only. The cockpit surfaces only the first question (matching Claude Code's UI), and the user's answer is sent back via the request's JSON-RPC response (`{answers: {<questionId>: {answers: [text]}}}`) rather than as new turn input. Grok Build presents multiple native questions one at a time and returns all answers in one reverse-RPC response. |

## Codex: feature-flag and deferred-work tracker

`codex features list` exposes feature flags that gate certain capabilities. Some of those flags affect cockpit features; this table records the cockpit's stance on each so we can revisit when Codex's defaults change.

| Codex feature | State in Codex | Cockpit stance |
|---|---|---|
| `default_mode_request_user_input` | experimental, off by default | **Wired, dormant.** The cockpit's `item/tool/requestUserInput` handler is fully implemented, but won't fire until Codex flips the flag (or a user opts in via `codex features enable default_mode_request_user_input`). |
| `memories` | experimental, off by default | **Not surfaced.** When on, Codex writes summaries to `~/.codex/memories/MEMORY.md` (global path, workspace-scoped via `applies_to: cwd=...` headers in the file). Doesn't fit the cockpit's per-workspace `getMemoryDir(workspacePath)` API; reconsider when the feature stabilizes. |
| Plan mode | stable in TUI; v2 plan delta protocol marked experimental | **Deliberately skipped.** Entry is strictly user-initiated (Shift+Tab keybind or `/plan` slash command); the model never auto-enters plan mode and there is no accept/reject gate after a normal turn — so it doesn't match the cockpit's "agent-decides, user-approves" UX. |

Grok implementation, native extensions, cost completeness, background work, and
platform verification are detailed in [spec-grok-build.md](docs/spec-grok-build.md).

CoCo compatibility is verified on 1.2.35/macOS arm64. Tool-enabled KB, Context,
Routine and OCR workflows are supported; strict CoCo Memory processors remain
disabled. ACP session MCP fields are not used: Cockpit supplies a private native
plugin. Saved sessions can load on an explicit next turn; interrupted work is
never automatically resent. Native Windows/Linux, human remote-browser Cockpit
acceptance and account isolation remain independent gates. See
[CoCo setup](docs/user/cortex-code.md) and the
[capability decisions](docs/research/cortex-code-capability-decisions.md).
